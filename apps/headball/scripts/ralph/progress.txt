## Codebase Patterns
- Migrations live in `supabase/migrations/NNNN_*.sql`. Apply locally with `bunx supabase db reset` (re-runs every migration from scratch — keep them idempotent or order-correct).
- All client writes go through Postgres SECURITY DEFINER functions. RLS only grants SELECT to `anon`; never add INSERT/UPDATE/DELETE policies for `anon`.
- Realtime: any new table the client subscribes to must be added to `supabase_realtime` publication via `alter publication supabase_realtime add table <name>;` inside the migration that creates it.
- Use `bun` / `bunx` (not npm). `bunx tsc --noEmit` for typecheck, `bun run lint` for lint.
- Local Postgres: `PGPASSWORD=postgres psql -h 127.0.0.1 -p 54322 -U postgres -d postgres` for ad-hoc verification queries.
- The schema in `docs/PLAN.md` line 105 has `index(category)` inside the table body — that is pseudocode, not valid PG. Use a separate `create index ... on football_players(category);` statement.
- Postgres functions that `returns table (room_id uuid, player_id uuid, ...)` create implicit OUT params that shadow table columns of the same name. Add `#variable_conflict use_column` after `as $$` so identifiers in the body resolve to columns.
- `position` is a reserved word in `returns table (...)`. Quote it: `returns table (..., "position" int, ...)`.
- `0002_*.sql` is now `0002_functions.sql` (atomic write fns). The seed migration referenced as `0002_seed_players.sql` in PLAN.md / US-003 must instead be authored as `0003_seed_players.sql`.
- Function security pattern: `security definer` + `set search_path = public`, then at the bottom `revoke execute ... from public; grant execute ... to anon;`. Anon never gets direct INSERT/UPDATE.
- SQL string literals: escape apostrophes by doubling them (`'N''Golo Kante'`). Backslash escapes do NOT work in PG standard strings.
- Seed migrations: rely on table unique constraints + `on conflict (...) do nothing` for idempotency. `bunx supabase db reset` runs migrations in numeric order; the legacy `supabase/seed.sql` is unused (benign warning).

Pattern: `page.getByRole("button", { name: /สร้างห้อง/ }).first()` for the page CTA, then `getByRole("dialog", { name: "ใส่ชื่อของคุณ" }).getByRole("button", { name: /^สร้างห้อง$/ })` for the dialog submit. Use the same trick anywhere a button label recurs inside its own dialog (future modals).
  - The unhandled-rejection error from realtime channels prints to the WebServer stderr but does NOT fail Playwright tests on its own — assertions fail downstream when the realtime push doesn't arrive. Don't ignore stderr noise from `[WebServer]` lines; it's the canary for race conditions in the realtime layer.

- **Learnings for future iterations:**
  - supabase-js serializes RPCs on a single `SupabaseClient` instance — they share an HTTP/1.1 keepalive connection and queue. To actually exercise PG-level concurrency you MUST instantiate two separate clients (`createClient(...)` × 2) and only THEN `Promise.all(...)`. Reusing one client makes the test pass trivially because the RPCs run in serial order on the wire and never collide on the row lock at all. Apply this to any future "race" / "concurrency" spec.
  - Playwright tests can drive Supabase RPCs directly via the same `@supabase/supabase-js` client the app uses — no browser context required when the property under test is server-side. Pattern: import `createClient<Database>(URL, ANON_KEY, { auth: { persistSession: false, autoRefreshToken: false } })` and call `.rpc('<fn>', { ...args })`. Saves the cost of spinning up N browser pages just to exercise N parallel HTTP calls.
  - Anon-key fallback for E2E: hardcode the local-dev publishable key (`sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH` — same on every machine) and let `process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY` override. Mirrors `admin.ts`'s service-role fallback. Playwright's test runner does not auto-load `.env.local` (only the dev server inherits it via `bun run dev`), so without the fallback specs fail with "Invalid API key" the moment they try to call an anon RPC outside a browser context.
  - The race property holds because `submit_guess` does `update round_positions set next_position = next_position + 1 ... returning next_position - 1` and `start_round` seeds `round_positions(next_position=1)`. PG's row-level lock on the UPDATE serializes the two writers automatically — no advisory lock or `FOR UPDATE` block needed on `round_positions` itself, because UPDATE already takes the row's exclusive lock. If a future change ever splits this into a `SELECT next_position` + `UPDATE next_position = $next` pair, the property will silently break and this spec will catch it.
  - `submit_guess` returns `setof record` typed as `{correct, position, score}[]` in `database.types.ts` — first element is the row. Always `data[0]`, not `data`.

  - The FOUL overlay (`<div role="status" aria-label="Foul" class="... motion-safe:animate-hb-flash">`) lives in the DOM for ~600ms but its hb-flash keyframe ends at opacity 0 with `forwards`. Asserting it with `toBeVisible` is a flake — Playwright's visibility check races the animation's final frame and the React `setTimeout(() => setFeedback(null), 600)` cleanup. Use `toBeAttached` instead: element-in-DOM is sufficient proof of the foul UI rendering, and the assertion is stable across CI loads. Same pattern applies to any future short-lived flash overlay (success flash, transient toasts).
  - `round_events.type` is the column name — NOT `event_type`. The enum is named `event_type` but the column is `type`. Generated `database.types.ts` reflects this. When asserting on the audit log, `.select("type").eq("type", "FOUL")`.
  - Black-box reconnect testing: re-declare the localStorage key constant (`PLAYER_ID_KEY = "headball_player_id"`) in the spec rather than importing `PLAYER_ID_STORAGE_KEY` from `lib/game-store.ts`. The spec is testing the persistence contract from the user's perspective — if a refactor changes the constant in app code without updating the spec, that's a real regression worth catching, not a coupling to fix.
  - `page.evaluate((key) => localStorage.getItem(key), KEY)` is the right way to read browser storage from a Playwright spec. Don't try to use `page.context().storageState()` — that returns a snapshot, not live state, and serializes the whole context including cookies.
