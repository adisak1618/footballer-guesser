## Codebase Patterns
- Migrations live in `supabase/migrations/NNNN_*.sql`. Apply locally with `bunx supabase db reset` (re-runs every migration from scratch — keep them idempotent or order-correct).
- All client writes go through Postgres SECURITY DEFINER functions. RLS only grants SELECT to `anon`; never add INSERT/UPDATE/DELETE policies for `anon`.
- Realtime: any new table the client subscribes to must be added to `supabase_realtime` publication via `alter publication supabase_realtime add table <name>;` inside the migration that creates it.
- Use `bun` / `bunx` (not npm). `bunx tsc --noEmit` for typecheck, `bun run lint` for lint.
- Local Postgres: `PGPASSWORD=postgres psql -h 127.0.0.1 -p 54322 -U postgres -d postgres` for ad-hoc verification queries.
- The schema in `docs/PLAN.md` line 105 has `index(category)` inside the table body — that is pseudocode, not valid PG. Use a separate `create index ... on football_players(category);` statement.
- Postgres functions that `returns table (room_id uuid, player_id uuid, ...)` create implicit OUT params that shadow table columns of the same name. Add `#variable_conflict use_column` after `as $$` so identifiers in the body resolve to columns.
- `position` is a reserved word in `returns table (...)`. Quote it: `returns table (..., "position" int, ...)`.
- `0002_*.sql` is now `0002_functions.sql` (atomic write fns). The seed migration referenced as `0002_seed_players.sql` in PLAN.md / US-003 must instead be authored as `0003_seed_players.sql`.
- Function security pattern: `security definer` + `set search_path = public`, then at the bottom `revoke execute ... from public; grant execute ... to anon;`. Anon never gets direct INSERT/UPDATE.
- SQL string literals: escape apostrophes by doubling them (`'N''Golo Kante'`). Backslash escapes do NOT work in PG standard strings.
- Seed migrations: rely on table unique constraints + `on conflict (...) do nothing` for idempotency. `bunx supabase db reset` runs migrations in numeric order; the legacy `supabase/seed.sql` is unused (benign warning).
- Validate `scripts/ralph/prd.json` with `bunx node -e "JSON.parse(require('fs').readFileSync('scripts/ralph/prd.json','utf8'))"` at the start of every iteration — past iterations have left it malformed.
- PG → Thai error mapping for `join_room`: P0002 → 'ห้องไม่พบ', P0003 → 'เกมเริ่มแล้ว', P0004 → 'ห้องเต็ม', P0001 → 'ชื่อไม่ถูกต้อง'. Always switch on `error.code` (not message). Verify codes via `do $$ ... exception when others then raise notice 'code=%, msg=%', SQLSTATE, SQLERRM; $$;` in psql.
- Server actions that wrap a single RPC don't need the `lib/room-code.ts`-style helper — call `supabase.rpc('<fn>', { ... })` directly, then dispatch a custom error mapper. Reserve helper modules for retry-loops or multi-statement orchestration.
- Sanitize the room-code input on every keystroke: `value.toUpperCase().replace(/[^A-Z0-9]/g, '').slice(0, 6)`. The displayed value mirrors what Zod accepts so users never see "valid-but-rejected" states.
- Form fields with two errors should split the state shape: `{ code?, name?, form? }` with `form` reserved for server-returned messages, and `code` / `name` for client-side Zod failures. Render each in its own slot — never merge into a single string or you lose `aria-describedby` precision.
- `bunx supabase gen types typescript --local` writes log lines ("Saved lockfile", "Connecting to db 5432") to stderr; using `> file` alone leaves stdout clean, but `2>&1 > file` will pollute the output. Use `bunx supabase gen types typescript --local 2>/dev/null > lib/database.types.ts` or just plain `>` redirect.
- Supabase browser client lives in `lib/supabase.ts` and uses `@supabase/ssr`'s `createBrowserClient<Database>` — pass the generated `Database` type so RPC calls (`.rpc('submit_guess', {...})`) get typed args + return shape automatically.
- Re-export row/RPC types from `lib/types.ts` (`Room`, `Player`, `RoundState`, `RoundEvent`, `RoomStatus`, `EventType`, `CreateRoomArgs/Result`, `JoinRoomArgs/Result`, `StartRoundArgs`, `SubmitGuessArgs/Result`). Future stories should import from `@/lib/types`, not from `lib/database.types` directly.
- Room code alphabet is `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (32 chars, no 0/O/1/I). Server side lives in `0002_functions.sql` create_room, client side in `lib/room-code.ts` (`ROOM_CODE_ALPHABET`). Keep these in sync if the alphabet ever changes.
- Postgres unique-violation error code is `23505` — surface it as `error.code` from a `supabase.rpc(...)` response. Use this code (not message string matching) for retry logic.
- Stadium Energy design tokens live in `app/globals.css` `@theme inline` block — colors (`--color-ink`, `--color-goal`, `--color-on-dark*`, `--color-tag-*`, `--color-surface*`, etc.) and font aliases (`--font-hero`=Bebas, `--font-display`=Anton, `--font-body`=IBM Plex Thai). Tailwind v4 auto-derives utilities like `bg-ink`, `text-on-dark-soft`, `font-display`. NEVER use Tailwind arbitrary color values — extend tokens here instead.
- Fonts loaded via `next/font/google` in `app/layout.tsx`: `Anton` (display), `Bebas_Neue` (hero/scoreboard), `IBM_Plex_Sans_Thai_Looped` (body, weights 400/500/600/700, subsets `["thai","latin"]`). All three are wired as CSS variables and the body element gets `bg-ink text-on-dark font-body` so screens inherit Stadium defaults.
- `<html lang="th">` — Thai-only at launch. Don't reset to `en`.
- For Thai-only button labels, use the body font (IBM Plex Thai). The DESIGN.md `button-lg` token specifies Anton, but Anton has no Thai glyphs. Pragmatic rule: Anton/Bebas only for Latin all-caps content (HEADBALL, ROUND 2, scores, room code).
- Server-side Supabase client lives in `lib/supabase-server.ts` — uses `createClient` from `@supabase/supabase-js` with `auth: { persistSession: false, autoRefreshToken: false }`. Use this from Server Actions / route handlers. The `@supabase/ssr` `createBrowserClient` in `lib/supabase.ts` is browser-only. Both share the same `SupabaseClient<Database>` type so helpers in `lib/room-code.ts` etc. accept either.
- Server Actions live in `app/actions/<verb>-<noun>.ts` with a top-level `"use server"` directive. Pattern: validate input with a Zod schema (compose existing schemas from `lib/schemas.ts`), instantiate `createSupabaseServerClient()`, call the helper, return a discriminated `{ ok: true, ... } | { ok: false, error: string }`. Errors must already be Thai-localized strings — UI just renders `result.error`.
- Zod v4 `z.uuid()` validates RFC 4122 strictly: requires the version nibble (1/2/3/4/5/7/8) at char 14 AND the variant nibble (8/9/a/b) at char 19. PG's `uuid` type accepts any 32-hex-char shape, so a "looks-like-a-UUID" string can pass PG and fail Zod. Always generate test UUIDs via `crypto.randomUUID()`, not by typing `33333333-4444-5555-6666-777777777777` (variant nibble is `6` → fails).

  - `createBrowserClient` from `@supabase/ssr` is browser-only — using it inside a Server Action throws at the first call. Server Actions need `createSupabaseServerClient()` from `lib/supabase-server.ts` (plain `@supabase/supabase-js` client with `auth: { persistSession: false, autoRefreshToken: false }`). Both share the same `SupabaseClient<Database>` type, so existing helpers like `createRoomWithRetry(supabase, ...)` accept either one with no overload juggling.
  - Zod v4 `z.uuid()` enforces RFC 4122 strictly (version + variant nibbles). PG accepts looser UUIDs, so a string like `33333333-4444-5555-6666-777777777777` clears PG but fails Zod's variant check (`6` is not in `8/9/a/b`). For the playerId payload always source from `crypto.randomUUID()` / `getOrCreatePlayerId()`; never invent test UUIDs by typing repeated digits.
  - The shadcn `Dialog` (base-ui Popup) ships with `bg-popover` / `text-popover-foreground` (shadcn's light theme). Building a Stadium-themed modal directly with a custom `<div role="dialog" aria-modal="true">` + click-outside dismiss + Escape handler is ~30 lines and avoids the theme conflict. Future modals (guess modal, reconnect modal) can follow the same pattern: `fixed inset-0 z-50 bg-black/70` overlay, `bg-surface border border-hairline rounded-2xl` content, controls disabled while `isPending`.
  - Server action input shape `{ displayName, playerId }` (plain JSON object) keeps callers ergonomic — FormData is harder to thread typed payloads through. Action returns a discriminated union (`ok: true/false`) so the client renders errors with one ternary.
  - `useTransition` is the right primitive for dispatching the action: it gives `isPending` automatically and blocks duplicate submits. `router.push(...)` only happens after the action resolves with `ok: true`, so no need to handle race conditions on close.
  - `getOrCreatePlayerId()` throws on SSR (it touches `localStorage`). Call it inside the form submit handler, not at component top-level — that way the SSR render of `<CreateRoomButton/>` stays clean.
  - Server action defaults (`max_rounds=5`, `score_positions=3`) are hard-coded constants `DEFAULT_MAX_ROUNDS` / `DEFAULT_SCORE_POSITIONS` at the top of the action file. Future settings UI (not in scope) would surface these — keep them as exported constants if a settings screen ever needs them.
  - `category='premier-league'` mentioned in the PRD acceptance is satisfied by the `rooms.category` DEFAULT in `0001_init.sql` — the `create_room` PG function never accepts a category arg, so the action doesn't pass one. Don't add an extra arg "to be safe"; it would break the function signature.

- **Learnings for future iterations:**
  - `safeParse` discriminated narrowing only works if you guard with `if (!a.success || !b.success)` and return inside that branch. Splitting checks across two separate `if` blocks then doing `if (next.code || next.name) return` will leave `a.data`/`b.data` typed as `string | undefined` and TS will reject downstream usage.
  - For dual-input forms, structure errors as `{ field1?, field2?, form? }` rather than a single string — the `form` slot is reserved for the server action's `result.error` and `field1/field2` for client Zod failures, so they render in distinct UI slots and `aria-describedby` stays precise.
  - Sanitize on input rather than on submit when the field has a hard charset (room code = uppercase alphanumeric only): `event.target.value.toUpperCase().replace(/[^A-Z0-9]/g, '').slice(0, 6)`. This means the user never sees a "valid-but-rejected" state — the input itself prevents typing illegal chars, even on paste.
  - `roomCodeSchema` already does `.trim().toUpperCase().regex(...)`, so the on-keystroke sanitizer and the schema converge on the same canonical form. Keep them aligned: if you change the alphabet in `lib/room-code.ts`, update both the regex and the keystroke filter.
  - Server actions wrapping a single RPC don't need a helper module like `lib/room-code.ts`. Call `supabase.rpc(...)` directly inside the action and feed the `error` object to a small inline `mapPgError` switch. Reserve helpers for retry-loops or multi-statement orchestration.
  - PG `RAISE EXCEPTION ... USING errcode = 'PXXXX'` codes propagate up through PostgREST as `error.code` on the supabase-js response — exactly the same surface as the `'23505'` unique-violation code. Always pattern-match on the code, never the message string (PostgREST may localize or rephrase).
  - Verifying error-code mapping is faster via psql than via TypeScript: `do $$ begin perform fn(...); exception when others then raise notice '%, %', SQLSTATE, SQLERRM; end$$;` prints the exact code+message pair in one statement.
  - `font-hero` (Bebas Neue) is the right token for the room-code input — DESIGN.md reserves it for "scoreboard / hero name / room code". Don't render it in `font-display` (Anton) or `font-body` (Plex Thai) — they break the Stadium aesthetic. Keep this consistent with the lobby's room-code display in US-010.
  - On the landing page, swap the inert "เข้าห้อง" button to `<Link>` (not a button-with-onClick) — this gives keyboard/middle-click/right-click semantics for free and keeps the page a server component. The visual classes are identical between `<Link>` and `<button>` in Tailwind.
