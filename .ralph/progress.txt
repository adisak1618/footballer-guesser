## Codebase Patterns

- Root `package.json` uses Bun workspaces (`apps/*`, `packages/*`). `apps/` and `packages/` dirs do not need to exist for `bun install` to succeed — empty globs are tolerated.
- Existing Headball app code lives at repo root through Phase 0; Phase 1 relocates it to `apps/headball/`.
- Turborepo v2 requires `packageManager` field in root `package.json` to resolve workspaces (currently `bun@1.1.29`).
- Turbo v2 schema uses `tasks` (not `pipeline`) — see `turbo.json`. Build outputs include `.next/**` (excluding cache) and `dist/**` for libraries.
- Bun 1.1.29 generates `bun.lockb` (binary), not `bun.lock` — turbo emits a harmless WARNING about parsing the lockfile but still functions; upgrading to Bun ≥1.1.42 (text lockfile) would silence it.
- Pre-existing tech debt: root `bun run lint` reports thousands of errors (eslint scope issue / type-aware rules in deps) — predates Phase 0 work, not a regression. Phase 1 relocation will likely scope eslint to `apps/headball/` and reduce the surface.
- Workspace packages under `packages/*` declare `"main": "./src/index.ts"`, `"types": "./src/index.ts"`, and `"exports": { ".": "./src/index.ts" }` so consumers import TS source directly (no build step) — matches D3 in the design doc.
- `next lint` is removed in Next 16 — do NOT add `"lint": "next lint"` to per-app `package.json`. Use `eslint` directly when wiring per-app lint (Phase 0.4/0.7).
- `.turbo/` (per-package turbo cache + logs) is gitignored at the repo root — covers every workspace package without repeating in each.
- Shared TS config lives at `tsconfig.base.json` (root). Apps/packages extend via `"extends": "../../tsconfig.base.json"`. Base owns `target/module/strict/jsx/baseUrl/paths`; consumers add only Next plugin + `include`. Don't redeclare `paths` per-package.
- `@social-hub/*` path alias resolves to `packages/*/src/index.ts` (set in base). Consume with `import { X } from "@social-hub/core"` — no deep imports (matches D3).
- Root `tsconfig.json` (existing Headball app) does NOT extend base by design — it stays Next-13-style for the legacy root app until Phase 1 relocates Headball into `apps/headball/` and that app gets its own base-extending tsconfig.
- `bunx tsc --noEmit` from a sub-dir (e.g. `cd apps/hub && bunx tsc --noEmit`) picks up that workspace's tsconfig — useful for verifying per-package extends work.
- `data/` directory stays at workspace root through Phase 1 (root `scripts/build-seed.ts` resolves it via `path.join(ROOT, "data")` where ROOT = `..` from scripts/). `apps/headball/tsconfig.json` adds `@/data/*` → `../../data/*` so headball code can keep using `import { ... } from "@/data/premier-league"` after the relocation without changing imports.
- `vitest.setup.ts` was moved into `apps/headball/` during US-008 (not just US-009 territory). Reason: `bunx tsc --noEmit` from `apps/headball/` needs to compile a file that imports `@testing-library/jest-dom/vitest` so Vitest's `Assertion` interface is augmented with `toBeInTheDocument`/`toHaveTextContent`. Without that file inside the project's tsconfig include, every test file using those matchers fails typecheck.
- After Phase 1.1 (US-008), root `package.json` keeps only workspace tooling: `turbo`, `typescript`, `supabase` (CLI used at workspace root), `@types/node` (for scripts/*.ts). Every Next/React/test library lives in `apps/headball/package.json`.
- Root scripts (`dev`, `build`, `lint`, `test`) are now Turbo proxies (`turbo run <task> --filter=@social-hub/headball` for the single-app tasks). Workspace-root `next dev` won't work after Phase 1.1 because `next.config.ts` / `tsconfig.json` still live at root through US-009 — by design.

Root `package.json` `seed:*` scripts now point to `apps/headball/scripts/*.ts`.

- **packages/core game-agnostic API shape (FR-2.1):** when extracting a primitive that takes a typed Supabase Database in headball, do NOT propagate the `Database` generic into packages/core. Instead: (a) accept `SupabaseClient` (default-typed, Database=any), (b) make the RPC's args/result types call-site generics with `unknown` defaults (`<TArgs = unknown, TResult = unknown>`), (c) cast inside core (`args as Record<string, unknown>`) to satisfy supabase-js v2 rpc typing. Consumers like headball pass their own `CreateRoomArgs`/`CreateRoomResult` from `@/lib/types` at the call site. This keeps packages/core a pure cross-game primitive while preserving end-to-end type safety in apps. Pattern established by US-014 (room-code); expected to repeat for US-015 (supabase clients, accept `<TDB>` generic), US-016 (dispatch wrapper), US-018 (player-id helper).
- **packages/core test discovery:** workspace-root `vitest.config.ts` `projects` array must list `packages/core` explicitly (not the glob `packages/*`) because packages/{ui,types,content} don't yet have `vitest.config.ts`. As future packages add their own configs, append them to the projects array. Each package owns its own vitest plugins/aliases/setup; use `environment: "node"` for pure-logic packages (no jsdom).
- **Vitest project labels:** when running `bunx vitest run --reporter=verbose`, tests from workspace packages are prefixed with `|@social-hub/<name>| src/path/to/test.ts` instead of just the path. Useful sanity check that a test moved to a package is actually being collected from that package, not double-collected from the old location.
- **packages/core dispatch wrapper (per US-016 / C1.B):** every cross-game RPC call in apps goes through `dispatch<TArgs, TResult>(supabase, rpcName, args)` from `@social-hub/core`. It unwraps array results to row[0], throws `GameRpcError` with `{ code, message, context: { rpc, args } }` on failure, and parses Postgres errcode via `parsePgErrCode` (returns `"UNKNOWN"` if absent). Postgres functions raise with `using errcode = 'PGAMExx'` per ranges in `packages/core/error-codes.md`: PGAME01–09 cross-game, PGAME10–49 Insider, PGAME50–89 future, PGAME90–99 platform.
- **packages/core typing convention (FR-2.1, reaffirmed by US-014/015/016):** primitives that wrap Supabase calls (`createRoomWithRetry`, `dispatch`) accept default-typed `SupabaseClient` (Database=any) and use call-site generics for args/result with `unknown` defaults. Cast `args as Record<string, unknown>` inside core to satisfy supabase-js v2 rpc typing. Apps preserve end-to-end type safety by passing their own arg/result types at the call site. Don't propagate `Database` into core. Singleton browser clients (which need a Database type) stay app-local.
- **`"use client"` required on every React hook in packages/* (per US-017):** any file under `packages/*/src/` that imports from `"react"` (`useState`, `useEffect`, `useRef`, etc.) MUST begin with `"use client"`. Reason: `packages/core/src/index.ts` is a barrel re-export consumed by both Next server actions (`apps/*/app/actions/*.ts`) and client components. Without the directive, Next 16 RSC errors at build time: "importing a module that depends on `useRef` into a React Server Component module". The directive marks the file as a client boundary so server consumers compile through it cleanly. Add `react` to BOTH `peerDependencies` AND `devDependencies` of the package (mirror the `@supabase/ssr` pattern). Established by `useRoomRealtime`; will repeat for any future hook in core/ui.
- **Realtime/effect hook callback-ref pattern (per US-017):** when a custom hook in packages/core takes consumer callbacks (`onChange`, `onReconnect`, `onStatusChange`) and the consumer naturally passes inline `useCallback` closures, store each callback in a `useRef` and update the ref via a tiny separate `useEffect`. The main effect (channel subscribe/unsubscribe) then depends only on stable structural inputs (e.g., `[supabase, roomId, tablesKey]`), NOT the callback identities. Otherwise every render that produces a new callback identity would tear down and resubscribe the Realtime channel. For array inputs that can't be stable (e.g., `tables: {table, filter}[]`), derive a `tablesKey = tables.map(...).join("|")` string and use the string in deps. Consumer should `useMemo` the array on the relevant roomId so the strings themselves don't churn either. Reusable for future Insider round-phase subscription (T-2.A).
- **Tailwind v4 + workspace UI package source discovery (per US-019):** Tailwind v4 (`@tailwindcss/postcss`) auto-discovers utility usage from the consuming app's tree but does NOT scan workspace symlinks under `node_modules/@social-hub/*`. To make `<Button />` from `@social-hub/ui` emit its classes, every consuming app's globals.css must include an explicit `@source "../../../packages/ui/src";` directive (path relative to the CSS file). Without it, classes used only inside packages/ui are silently dropped from the bundle. There is no JS `tailwind.config.ts` to register paths in v4 — it's CSS-first. Reusable for any future workspace UI consumer (apps/hub, apps/insider).
- **Stadium Energy tokens canonical source (per US-019):** `packages/ui/src/tokens.css` is the documentation reference; the actual functional copy lives inlined in each app's `app/globals.css` inside a Tailwind v4 `@theme inline { ... }` block (Tailwind v4 doesn't yet support importing `@theme` blocks across packages). When a token changes, update BOTH places. The duplication is intentional until Tailwind ships cross-package `@theme` import support. Stadium Energy tokens defined: surfaces (ink, surface, surface-elevated, hairline*, canvas, surface-soft, surface-card), text (on-dark*, on-light*), primary action (goal, goal-active, goal-disabled), player tags (red/blue/yellow/green/purple/orange/pink/cyan), semantic (success/warning/error/info), fonts (hero=Bebas, display=Anton, body=PlexThai), animations (hb-shake, hb-flash, hb-pop).
- **packages/ui peer-dep convention (per US-019):** UI primitives package declares React, react-dom, @base-ui/react, lucide-react as `peerDependencies` (single React tree across the workspace) and bundles class-variance-authority, clsx, tailwind-merge as direct `dependencies` (utility libs, no singleton concerns). Mirror this for any future shared UI package.
- **packages/ui vitest config quirk (per US-019):** packages/ui's `vitest.config.ts` should NOT load tsx files in tests unless `@vitejs/plugin-react` is wired. Default rolldown ssrTransform fails to parse JSX. Keep package-level smoke tests on pure-TS exports (e.g., `cn` from `./utils`) — render tests belong in apps where the React plugin is already configured.

- **Learnings:**
  - **dispatch unwraps array results**: Postgres functions declared `returns setof <type>` come back through supabase-js as `data: row[]` even when only one row is returned. dispatch detects `Array.isArray(data)` and returns `data[0]`; otherwise returns `data` unchanged. This matches the `createRoomWithRetry` pattern in room-code.ts and means consumers don't need to write `(await dispatch(...))[0]` everywhere.
  - **PGAMExx vs Postgres SQLSTATE**: Postgres SQLSTATE is canonically 5 chars; the design doc's `using errcode = 'PGAME01'` (7 chars) may be rejected at apply time. The dispatch wrapper is intentionally agnostic — it returns whatever string lives in `error.code`. If migrations need to fall back to a 5-char code, only the migration changes; the wrapper still works. Documented this caveat in error-codes.md so future migrations don't get blindsided.
  - **GameRpcError context shape**: `context = { rpc: <rpcName>, args: <args> }` is the contract. Don't extend it without updating callers — UI error boundaries and Sentry/logging layers will eventually destructure these two fields.
  - **error.message fallback**: when `error.message` is missing (e.g., supabase returns `{}` for some network conditions), dispatch synthesizes `"RPC <name> failed"` so GameRpcError always has a non-empty message string. Necessary because `super(undefined)` on Error gives `message: ""` which fails downstream string checks.

  - **"use client" required on barrel-exported hooks (Next 16 RSC):** when `packages/core/src/index.ts` re-exports a module that imports `useRef`/`useEffect` from `react`, ANY server-side import of `@social-hub/core` (e.g., `apps/headball/app/actions/create-room.ts`, a server action that imports `dispatch` or `createRoomWithRetry`) will pull the hook through the barrel and Next 16 errors at build time: "You're importing a module that depends on `useRef` into a React Server Component module." Fix: add `"use client"` as the first line of the hook file. Marks the file as a client-only boundary; Next compiles server consumers to call into it correctly. This will recur for every future React hook added to packages/core (US-018 player-id helper if it becomes a hook, future UI hooks). Pattern: any `packages/*` file importing from `react` MUST start with `"use client"`.
  - **packages/core React peer dep policy:** add `react` to BOTH `peerDependencies` AND `devDependencies`. Peer dep declares the ambient React version requirement (so consumers like apps/headball provide it); dev dep makes type-check work in isolation (e.g., `cd packages/core && bunx tsc --noEmit`). Match the existing pattern used for `@supabase/ssr` and `@supabase/supabase-js` in this same package.json.
  - **realtime hook callback-ref pattern:** the consumer in apps/headball wants to pass `onChange`/`onReconnect`/`onStatusChange` as inline `useCallback` closures that close over store setters. If the effect deps included those callbacks, every render that produced a new callback identity would tear down + resubscribe the channel — bad for Realtime. Solution: store callbacks in `useRef` and update the ref in a separate `useEffect` per callback. Effect that creates the channel only depends on `[supabase, roomId, tablesKey]`. This pattern is reusable for any future "hook with callbacks that should not retrigger subscription" — Insider's round-phase subscription (T-2.A) likely needs the same.
  - **`tablesKey` for stable subscribe:** the hook accepts `tables: { table; filter? }[]` which is structurally a new array every render. Computing `tablesKey = tables.map(t => `${t.table}:${t.filter ?? ""}`).join("|")` and using THAT in the effect deps means the subscription only resets when the list of (table, filter) pairs actually changes, not on every render. Consumer-side: wrap the array in `useMemo` keyed on roomId so the strings themselves don't churn either.
  - **roomId lifted to React state:** previously `knownRoomId` was an effect-local mutable variable; the hook needs roomId reactively, so the page now uses `useState<string | null>(null)`. On unmount we clear via `setRoomId(null)` in addition to `reset()`.
  - **Postgres types in core hook:** `RealtimePostgresChangesPayload<Record<string, unknown>>` is the most precise generic the hook can offer without baking in headball schema. Apps cast `payload.new as Room` at the call site (matches the FR-2.1 pattern of "core stays game-agnostic, apps reattach types").
  - **`.on("postgres_changes" as never, ...)`:** supabase-js v2 `RealtimeChannel.on` has overloaded signatures keyed on the first arg. Without the overload tightening, TS infers the wrong overload when filter is conditional. Casting the literal `"postgres_changes"` to `never` lets the call resolve cleanly without giving up payload typing. (Used inside core; apps don't see this.)
