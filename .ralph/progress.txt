## Codebase Patterns

- Zustand persist + jsdom test gotcha: Node 25 forwards a `--localstorage-file`
  flag to vitest workers that activates Node's built-in `localStorage` WITHOUT
  a valid path → it becomes a non-functional stub that *shadows* jsdom's
  working localStorage. Tests that touch `localStorage` must install an
  in-memory `Storage` shim via `Object.defineProperty(window/globalThis,
  'localStorage', {value, configurable: true})` BEFORE dynamically importing
  the module under test (see `apps/warewolf/lib/store.test.ts`). Production
  code is unaffected — browsers provide a real localStorage.
- `<CardArt>` is the only component that should ever render a card image —
  callers never reach for raw `next/image` against `cardArtPath(...)`. Its
  `onError` falls through to `<CardArtPlaceholder>` (Grimoire empty card with
  wax-seal silhouette + role name + signed balance badge), so a 404 never
  surfaces the browser's broken-image icon (Eng Review failure-mode #2).
  Sizes: `sm` (60×90, setup-card thumb), `md` (84×126, customize grid),
  `lg` (240×360, role-detail modal). Both are `"use client"` (the error
  fallback needs state); fine to use in server components — Next collapses
  the boundary at the component.
- Component tests (`apps/warewolf/components/**/*.test.tsx`) opt INTO the
  jsdom environment with a top-of-file `// @vitest-environment jsdom`
  directive. The vitest config keeps `environment: "node"` as the default
  so lib/* / scripts/* pure-TS tests stay fast. Deps to be aware of:
  `@vitejs/plugin-react`, `@testing-library/react`, `@testing-library/jest-dom`,
  `jsdom` — all already declared in apps/warewolf/package.json (mirrors the
  pattern in apps/headball). The vitest setup file (`vitest.setup.ts`)
  imports `@testing-library/jest-dom/vitest` so `toBeInTheDocument` etc.
  work; node-env tests load it harmlessly.
- When unit-testing components that wrap `next/image`, mock it to a plain
  `<img>` via `vi.mock("next/image", ...)`. Strip the `priority` boolean
  before spreading so React doesn't warn about non-DOM attrs.
- Client-Component pages that call `useSearchParams()` MUST be wrapped in
  `<Suspense fallback={...}>` or Next 16's static-export pass fails the
  build with "useSearchParams() should be wrapped in a suspense boundary".
  Pattern (see `apps/warewolf/app/[lang]/setup/page.tsx`): outer
  `export default function FooPage()` returns
  `<Suspense fallback={null}><FooPageInner /></Suspense>`; inner
  `function FooPageInner()` owns the `useSearchParams` + `useRouter`
  logic. Same restriction applies to `useRouter` reads of `?query`.

- Grimoire design tokens live in `docs/DESIGN-warewolf.md` (canonical) and are
  mirrored into `apps/warewolf/app/globals.css` (Tailwind v4 `@theme inline`).
  Token names match 1:1 between the two — when changing one, change the other
  in lockstep. Headball's Stadium Energy in `docs/DESIGN.md` is a SEPARATE
  system; do NOT cross-pollinate. Prototype `finalized.html:17-34` is the
  visual ground truth for hex values (the earlier design-doc text's
  `#f6ebd0` off-cream is superseded by the prototype's `--cream: #fbf4e0`).
- `@social-hub/content` is the cross-app source of truth for static role/content data.
  Place new role-data modules under `packages/content/src/` (NOT the package root) so
  the existing `tsconfig.json` (`include: ["src/**/*.ts"]`) and `vitest.config.ts`
  (`include: ["src/**/*.test.ts"]`) pick them up. Re-export from `src/index.ts`.
- Tests live next to the source as `src/<name>.test.ts` (vitest picks them up via
  the workspace-root vitest projects pointer plus the package-local config).
- Spec/typo note for V1 warewolf roles: design doc + story US-001 both say
  "22 V1 roles" but enumerate 25 named role IDs (5 wolf + 4 info + 8 power +
  4 vanilla + 4 neutral). The prototype `finalized.html` also has 25. Treat the

- Role.category enum is fine-grained (info/protection/kill/vote/chaos/vanilla/neutral);
  the customize-page 6-tab mapping in `lib/category-tabs.ts` (Eng Review decision #6)
  derives display tabs from team + category. Do not collapse the enum to match the
  prototype's coarse wolf/info/power/social/neutral.
- Lane A (US-002..US-008) files live under `apps/warewolf/lib/` but US-009

  typecheck + tests work, US-002 added minimal `apps/warewolf/{package.json,

- Solver SetupListItem is a discriminated union: Setup | SolverError (kind:
  'solver-error'). `isSolverError(item)` type-guards in consumers. Non-error
  rows sort by |balance| ASC; errors append at the end in archetype-declaration

  Use `import fc from "fast-check"` for property tests; `fc.constantFrom(...ids)`
  + `fc.array` compose nicely with ROLE_IDS filters by team.
- Validator (`lib/validator.ts`) is single-pass and strict: unknown role ids are
  blockers (`'unknown-role'`). The parser (`lib/share-url.ts`, US-007) is the
  sole place that silently substitutes unknowns to `villager` — keep that
  single source-of-truth split per Eng Review decision #3.
- `zod` 4.3.6 is hoisted at the workspace root via Headball; warewolf declares
  `"zod": "^4.3.6"` in `apps/warewolf/package.json` to make the dependency
  explicit. Schemas with `.catch(fallback)` swallow validation errors and
  return the fallback — useful for graceful URL parsing where the URL is
  user-modifiable.
- decodeSetup pre-filters `lang` to `'en' | 'th' | undefined` BEFORE handing to
  Zod, so invalid values (e.g. `?lang=fr`) trigger `.default('en')` instead of
  the enum throwing. Same pattern works for any z.enum field reachable from
  user input.
- Tailwind v4 `@theme inline` block in `apps/warewolf/app/globals.css` mirrors
  `docs/DESIGN-warewolf.md` 1:1 (parchment/ink/blood/cream + serif fonts +
  type/spacing/motion scale). PostCSS at workspace root (`postcss.config.mjs`)
  is shared across all apps via `@tailwindcss/postcss`. When tokens change,
  update DESIGN-warewolf.md AND globals.css in lockstep — neither is
  authoritative alone; they are mutually-consistent sources for human + compiler.
- Warewolf root layout chain (post-US-011): `app/layout.tsx` is a pure
  passthrough (returns `children`); `app/[lang]/layout.tsx` owns
  `<html lang={lang}><body>` with the dynamic locale and wraps children in
  `NextIntlClientProvider`. Calls `setRequestLocale(lang)` so child server
  components see the locale, and `generateStaticParams()` enumerates the
  routing locales for SSG. Don't put `<html>` in both layouts — Next.js
  renders only one.
- Warewolf dev port is 3003 (headball=3000, hub=3001, insider=3002). Reflected
  in both `package.json` dev script and `playwright.config.ts` PORT default.
- next-intl v4 wiring lives in three files: `i18n/routing.ts` (defineRouting
  with locales + defaultLocale), `i18n/request.ts` (getRequestConfig loading
  `messages/{lang}.json`), and the `next.config.ts` plugin
  `createNextIntlPlugin('./i18n/request.ts')`. `i18n.ts` at the package root
  is a thin re-export so the AC's "i18n.ts defines locales" sentence has a
  literal hit. Add a new locale by appending to `routing.ts` and creating
  the corresponding `messages/<locale>.json` — no other plumbing.
- Locale precedence (Eng Review decision #5) is enforced by
  `apps/warewolf/middleware.ts` BEFORE delegating to next-intl. The pure
  rule lives in `lib/locale-precedence.ts` (URL → 'passthrough' | redirect
  target) so it's unit-testable without booting Next. `?lang=` is treated
  as one-time backward-compat: matches segment → passthrough (param
  silently ignored downstream); mismatches → 301 to `/queryLang/...` with
  lang stripped from the new query. Unknown lang values (`?lang=fr`) →
  passthrough so next-intl can handle them via its own fallback.
- ICU MessageFormat is the i18n interpolation contract (Eng Review
  code-quality fix #2). Blocker codes carry their args in the message
  string: `wolves-gte-village: 'Too many wolves: {W} wolves vs {V} village'`,
  `role-count-mismatch: '{actual} roles selected for {expected} players'`,
  `no-wolves: 'No wolves — there is no game'`. UI consumers pass
  `{W, V}` / `{actual, expected}` to `t(...)` — never hand-format these
  strings with template literals.

- US-023 balance audit (`apps/warewolf/lib/solver-audit.test.ts`) cartesian-loops
  every visible (archetype × playerCount × variationIdx) cell and asserts
  |balance| ≤ 5. Solver throws are skipped (they render as <SolverErrorRow>),
  but |balance| > 5 is an immediate failure that names the offending tuple.
  Pairs with a perf-gate test asserting `computeSetupList(20) < 50ms`. If a cell
  fails post-data-change, FIX THE SEED OR WOLF POOL — never the threshold (per
  story US-023 Technical Notes).
- `social-bluff` variation 1 originally shipped from the prototype with village
  `[mason, mason, spellcaster, old-hag]` (sum 6). At playerCount=10 the solver
  needs target wolf sum -9 but the wolf pool's minimum 3-wolf sum is -15
  (werewolf+werewolf+sorceress or werewolf+minion+sorceress), so the cell
  rendered |balance|=6 and tripped the US-023 audit. Swapped `spellcaster` (+1)
  → `prince` (+3) lifting village sum to 8; entire 5–13 player span now lands
  |balance| ≤ 5. Vibe text updated to mention prince. See in-source comment
  block above the variation 1 entry for context.
