## Codebase Patterns

- Root `package.json` uses Bun workspaces (`apps/*`, `packages/*`). `apps/` and `packages/` dirs do not need to exist for `bun install` to succeed — empty globs are tolerated.
- Existing Headball app code lives at repo root through Phase 0; Phase 1 relocates it to `apps/headball/`.
- Turborepo v2 requires `packageManager` field in root `package.json` to resolve workspaces (currently `bun@1.1.29`).
- Turbo v2 schema uses `tasks` (not `pipeline`) — see `turbo.json`. Build outputs include `.next/**` (excluding cache) and `dist/**` for libraries.
- Bun 1.1.29 generates `bun.lockb` (binary), not `bun.lock` — turbo emits a harmless WARNING about parsing the lockfile but still functions; upgrading to Bun ≥1.1.42 (text lockfile) would silence it.
- Pre-existing tech debt: root `bun run lint` reports thousands of errors (eslint scope issue / type-aware rules in deps) — predates Phase 0 work, not a regression. Phase 1 relocation will likely scope eslint to `apps/headball/` and reduce the surface.
- Workspace packages under `packages/*` declare `"main": "./src/index.ts"`, `"types": "./src/index.ts"`, and `"exports": { ".": "./src/index.ts" }` so consumers import TS source directly (no build step) — matches D3 in the design doc.
- `next lint` is removed in Next 16 — do NOT add `"lint": "next lint"` to per-app `package.json`. Use `eslint` directly when wiring per-app lint (Phase 0.4/0.7).
- `.turbo/` (per-package turbo cache + logs) is gitignored at the repo root — covers every workspace package without repeating in each.
- Shared TS config lives at `tsconfig.base.json` (root). Apps/packages extend via `"extends": "../../tsconfig.base.json"`. Base owns `target/module/strict/jsx/baseUrl/paths`; consumers add only Next plugin + `include`. Don't redeclare `paths` per-package.
- `@social-hub/*` path alias resolves to `packages/*/src/index.ts` (set in base). Consume with `import { X } from "@social-hub/core"` — no deep imports (matches D3).
- Root `tsconfig.json` (existing Headball app) does NOT extend base by design — it stays Next-13-style for the legacy root app until Phase 1 relocates Headball into `apps/headball/` and that app gets its own base-extending tsconfig.
- `bunx tsc --noEmit` from a sub-dir (e.g. `cd apps/hub && bunx tsc --noEmit`) picks up that workspace's tsconfig — useful for verifying per-package extends work.

- **Learnings:**
  - In TS 4.1+ `paths` declared in an extended config are resolved relative to the base config's directory — so putting `baseUrl: "."` + `paths` in `tsconfig.base.json` at root means a consumer at `apps/hub/tsconfig.json` resolves `@social-hub/core` to `<root>/packages/core/src/index.ts` without re-declaring anything.
  - `include` and `exclude` are NOT inherited via `extends`; each consumer must declare its own. Keep them per-package.
  - `jsx` belongs in base (set to `preserve` for Next apps). React-only library packages don't render JSX in src yet, so `preserve` doesn't hurt them; if a package later needs `react-jsx` for tests, override locally.
  - The wildcard `paths` mapping `@social-hub/*` → `packages/*/src/index.ts` only resolves bare-package imports (`@social-hub/core`), not deep imports (`@social-hub/core/foo`). That matches D3's "barrel-export only" rule.
