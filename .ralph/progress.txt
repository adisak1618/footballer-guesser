## Codebase Patterns

- **Public-facing reconcile slice + helper coexistence (per US-047 / A3.B):** `expire_round(p_room_id, p_round)` is the single-purpose, public-facing RPC clients fire the moment their local asking-phase timer hits zero. It does ONE transition: `asking → result_failed` when the deadline has passed. It deliberately does NOT subsume `reconcile_round_phase` (migration 0020) — the helper still runs as the first line of every Insider mutation RPC and additionally handles `voting → reveal`. So the pattern is: clients call `expire_round` directly when their timer expires (broad fan-in, idempotent via WHERE-clause phase guard); inside any other RPC, the implicit `perform reconcile_round_phase(...)` chain absorbs the same transition AND the voting one. Don't merge the two — keep `expire_round` minimal and focused on what clients need to fire on a timer event. Reusable for any future "timer-driven public RPC" alongside an internal reconciler (e.g., a hypothetical `expire_voting` if voting eventually needs a public-facing form too — though today voting timeout is handled inside `advance_to_reveal`).
- **`returns int` for "rows affected" idempotency contracts (per US-047):** when an RPC's WHERE-clause guard is the idempotency mechanism (so two concurrent calls produce one winner + one no-op), declare it `returns int` and `get diagnostics v_count = row_count; return v_count;` after the UPDATE. Tests can then assert `a + b === 1` for two concurrent calls — strong evidence that exactly one mutation occurred. Cheaper and more truthful than re-reading the row to infer the count. Reusable for any future "first-fires-wins" RPC where the SQL UPDATE is the natural single source of truth (e.g., race-on-vote scenarios that don't need PK uniqueness violations).
- **Insider round bootstrap pattern (per US-044 / Phase 5a.7):** the canonical "host-starts-game" RPC for any new game (Insider's `start_insider_round`, future `start_<game>_round` analogues) follows a five-step shape: (1) `select … into v_host, v_status from rooms where id = p_room_id for update` — single locked read for both authorization and status gate; (2) authorization gate `if v_host <> p_player_id then raise PGAMExx using errcode = 'PGxxx'`; (3) `if v_status <> 'LOBBY' then raise …` — LOBBY-only entry; (4) `select count(*), array_agg(player_id order by random()) into v_count, v_player_ids from players where room_id = p_room_id` shuffles the roster in a single pass — slots [1..k] become the privileged roles, [k+1..N] become commons; (5) insert per-round state + per-player role rows via `generate_subscripts(v_player_ids, 1)`, then `update rooms set status = 'PLAYING', current_round = v_round_number`. The `for update` lock + status-flip combine to make the RPC effectively single-shot per game (a concurrent second call sees PLAYING and raises). Reusable for any future game that has a "host clicks Start" entry point.
- **Random shuffle in plpgsql via `array_agg(... order by random())`:** for assigning N players to ordered roles (master, insider, commons), do NOT loop with `random()`-based PL/pgSQL: a single `select array_agg(player_id order by random()) into v_player_ids from players where …` shuffles the entire roster in one pass. Then map roles by array index: `v_player_ids[1] = master`, `v_player_ids[2] = insider`, etc. Iterate the array via `generate_subscripts(arr, 1) as g(i)` in an INSERT...SELECT for the role rows. Idiomatic, deterministic per call (no read-then-update races), and works for any role-assignment shape. Reusable for any future "shuffle and assign" Insider/multi-role game RPC.
- **Public Insider sub-tables vs. secret-bearing tables (per US-040 / A1.C):** Insider per-round data splits cleanly into two RLS shapes. (1) Tables that carry NO asymmetric secret (`game_insider_roles`, `game_insider_responses`, `game_insider_votes`) use the simple shape: `enable row level security` + `for select to anon using (true)` + `alter publication supabase_realtime add table <t>` (no column list, no REVOKE/GRANT dance). Knowing roles/responses/votes does NOT leak the secret — the secret stays on `game_insider_round.secret_value` only. (2) Tables that DO carry an asymmetric secret (only `game_insider_round` so far) use the full column-level pattern from migration 0017. When adding a new Insider per-round table: default to shape (1) unless the table holds something only Master/Insider should ever read.
- **Column-level secret protection (per US-038 / A1.C):** for asymmetric-secret game tables (Insider's `secret_value`, future Master/Spy reveals), the pattern is: (a) create the table with all columns inline (NO split table), (b) `enable row level security` + permissive `for select to anon using (true)` policy, (c) `revoke select on <table> from anon` to strip Supabase's default broad grant, (d) `grant select (col1, col2, ...) on <table> to anon` enumerating ONLY non-secret columns, (e) Realtime publication MUST use explicit column list `alter publication supabase_realtime add table <t> (col1, col2, ...)` because column-level GRANTs do NOT filter Realtime payloads — without the column list, anon subscribers receive `secret_value` over the WebSocket. Master/Insider fetch the secret via SECURITY DEFINER RPC (e.g. `get_my_insider_secret`). Test signature: anon `select('*')` returns `error.code === '42501'` (insufficient_privilege), anon `select('secret_value')` also returns 42501, anon `select('non_secret_col1, non_secret_col2, ...')` returns the row WITHOUT secret_value. Apps's lint gate (`scripts/check-realtime-publication.sh`) tolerates the column-list form because the regex captures the table name and ignores the trailing `(...)`.

- **PGAMExx → 5-char SQLSTATE mapping (per US-025 / error-codes.md):** PostgreSQL rejects 7-char errcodes (`'PGAME01'`) as unrecognized exception conditions. Established mapping: `PGAMExx` → SQLSTATE `'PGxxx'` (class `PG` unreserved by PG; subclass = symbolic suffix zero-padded to 3 digits). E.g. `PGAME01 → PG001`, `PGAME10 → PG010`. Always embed the symbolic name at the start of the message (`'PGAME01: pack not found: %'`) so both `error.code` (SQLSTATE) and `error.message` (symbolic) carry the identifier. App-side error handling matches on `error.code === 'PG001'`. Headball-legacy `P0xxx` codes stay untouched (C4); only NEW cross-game / Insider RPCs use the new mapping.
- **`returns table(...)` plpgsql + qualified column refs (per US-025):** when a function declares `returns table(item_id text, display_value text, metadata jsonb)` and the body uses `return query select … wpi.metadata`, fully-qualify EVERY column in the select list. Bare unqualified column names that match an OUT parameter name (e.g., bare `metadata`) introduce ambiguity that PL/pgSQL resolves inconsistently across versions. Always: `wpi.metadata`, `fp.id`, etc.

RLS-protected tables require the service-role key; reuse the local fallback JWT pattern from `apps/headball/e2e/_helpers/admin.ts` so the script runs out of the box against `bunx supabase start` with no env setup. Staging-target runs require `SUPABASE_URL_STAGING` + `SUPABASE_SERVICE_ROLE_KEY_STAGING` env vars; defer until US-006 wires them.
- **Phase 4 rooms.game_type column (per US-031 / Phase 4 PRD):** `rooms` carries `game_type text not null default 'headball'` with `check (game_type in ('headball','insider'))` and a `rooms_game_type_idx` btree (cheap; hub will filter by `code` first but a small index helps future analytics). Existing Headball rows are unaffected (the default applies during the alter, so backfill is automatic). NO publication change needed — `rooms` is already in `supabase_realtime` and `alter table … add column` propagates to existing publications. The realtime-publication script only flags `create table`, so adding a column to an already-published table is invisible to it (correct behavior). When Insider lands (Phase 5+), its `create_room`-equivalent RPC must set `game_type := 'insider'`; the Headball `create_room` RPC keeps the default and needs no change (preserves C4 additive-only).
- **Database type regen — silence stderr (per US-028 / T-6 / FR-3.6):** the canonical Supabase types live at `packages/types/src/database.types.ts` and are re-exported from `@social-hub/types` (alongside `Json`). Apps import via `import type { Database } from "@social-hub/types"`. Regenerate after any migration that adds/alters a `public.*` table or function: `bunx supabase gen types typescript --local 2>/dev/null > packages/types/src/database.types.ts`. Don't import `Database` directly from a sibling app's lib dir; it's package-only now.
- **Insider RPC standard skeleton (per US-043 / T-3.B):** every Insider mutation RPC follows the same three-step skeleton: (1) `perform reconcile_round_phase(p_room_id, p_round)` — self-heal expired deadlines BEFORE inspecting phase; (2) authorization check — most commonly `if not exists (select 1 from players where room_id = p_room_id and player_id = p_player_id) then raise … using errcode = '<code>'` (PGAME11 = "not in room", SQLSTATE PG011); host-only RPCs additionally check `rooms.host_player_id = p_player_id`; (3) phase-guarded `update game_insider_round set phase = '<next>', … where … and phase = '<current>'` — the WHERE-clause phase filter is the idempotency mechanism (second call or wrong-phase call → zero rows updated → silent no-op, no error). Don't add IF/THEN branching for "phase already advanced" — let the WHERE clause absorb it. Pattern: `advance_to_asking` (preparing→asking) is the simplest instance; reused for `mark_correct_guess` (asking→guessed), `advance_to_reveal` (voting→reveal), etc.
- **PGAME11 = "player not in room" (per US-043):** binding assignment, supersedes the "already voted" example in `packages/core/error-codes.md`. Used when a SECURITY DEFINER Insider RPC needs to verify the caller is a member of `players` for the room. Membership check shape: `if not exists (select 1 from players where room_id = p_room_id and player_id = p_player_id)`. Raise with `using errcode = 'PG011'` (5-char SQLSTATE) and message prefix `'PGAME11: '`. Test signature: anon rpc call returns `{ error: { code: 'PG011', message: /PGAME11/ } }`. App-side handler matches on `error.code === 'PG011'`.
- **T-4 connected-players snapshot pattern (per US-046 / mark_correct_guess):** when an Insider RPC must capture "currently-connected players" into a uuid[] (e.g. `eligible_voter_ids` at vote start), do it inline inside the SAME UPDATE that flips the phase, via a sub-select: `update game_insider_round set …, eligible_voter_ids = (select array_agg(player_id) from players where room_id = p_room_id and connected = true) where …`. This keeps the snapshot atomic with the phase flip — there is no read-then-write window where a player could connect/disconnect between the SELECT and the UPDATE. Disconnected players are EXCLUDED from voting eligibility but voting still proceeds without waiting on them (T-4: 60s window, vote-completion fires when all eligible voters voted, not when all players voted). The `connected bool` column on `players` is the canonical presence signal — it is set by Realtime presence handlers in client code, NOT something Postgres maintains. Reusable for any future "snapshot connected players" need (e.g. score event eligibility, mid-round sync).
- **Master-only RPC pattern with role lookup (per US-045/US-046 / C2.A):** master-only Insider RPCs (`master_respond`, `mark_correct_guess`, future `master_*` RPCs) use a single combined SELECT to fetch BOTH `phase` from `game_insider_round` AND `role` from `game_insider_roles` via a left join keyed on `(room_id, round_number, player_id)`. The left join is critical: a stranger (no role row) yields `v_role IS NULL`, which the `if v_role is null or v_role <> 'master'` guard catches before any phase logic runs. This avoids a separate "is the caller in the room" check (PGAME11) for master-only RPCs — non-room callers fail the role check first with PGAME15. Three-tier guard order after reconcile: (1) role check → PGAME15, (2) `phase = 'result_failed'` → PGAME02 (post-reconcile expiry path), (3) `phase <> 'asking'` → PGAME16. Reusable for any master-only RPC running during the asking phase.
- **`reconcile_round_phase` self-healing helper (per US-041 / T-2.A):** every Insider RPC begins with `perform reconcile_round_phase(p_room_id, p_round)` so a missed `expire_round` (network blip, tab closed, race) is auto-fixed before the RPC inspects the phase. The helper is a SECURITY DEFINER function with two UPDATE statements: (1) `asking → result_failed` when `now() >= started_at + make_interval(secs => time_limit_s)`, (2) `voting → reveal` when `now() >= vote_deadline`. Other phases and not-yet-expired rounds are no-ops via WHERE-clause filtering — there is no IF/branching, just two filtered UPDATEs. This makes it idempotent (second call is also a no-op) and silent on missing rounds (UPDATE matches zero rows, no error). Use `make_interval(secs => time_limit_s)` rather than `interval '1 second' * time_limit_s` — the latter requires a cast and is less idiomatic. GRANT EXECUTE to anon is required because anon is the only role apps connect with; SECURITY DEFINER lets the helper UPDATE rows even though anon has no direct UPDATE on `game_insider_round`. Always `set search_path = public` on SECURITY DEFINER functions to defend against search_path attacks.

  - **"use client" required on barrel-exported hooks (Next 16 RSC):** when `packages/core/src/index.ts` re-exports a module that imports `useRef`/`useEffect` from `react`, ANY server-side import of `@social-hub/core` (e.g., `apps/headball/app/actions/create-room.ts`, a server action that imports `dispatch` or `createRoomWithRetry`) will pull the hook through the barrel and Next 16 errors at build time: "You're importing a module that depends on `useRef` into a React Server Component module." Solution: store callbacks in `useRef` and update the ref in a separate `useEffect` per callback. Effect that creates the channel only depends on `[supabase, roomId, tablesKey]`. This pattern is reusable for any future "hook with callbacks that should not retrigger subscription" — Insider's round-phase subscription (T-2.A) likely needs the same.

Computing `tablesKey = tables.map(t => `${t.table}:${t.filter ?? ""}`).join("|")` and using THAT in the effect deps means the subscription only resets when the list of (table, filter) pairs actually changes, not on every render.   - **Branching-free phase reconciliation:** the helper is implemented as two filtered UPDATEs rather than IF/CASE, which makes it (a) idempotent on already-resolved rounds (UPDATE matches zero rows on the second call), (b) silent on missing rounds (UPDATE matches zero rows, no exception), (c) order-insensitive (an `asking → result_failed` row will never match the `voting → reveal` UPDATE). A naïve IF-based version would need explicit existence checks and EXCEPTION handling for "no row" cases; the WHERE-clause approach handles all of that for free. Reusable for any future "self-healing state machine" Postgres function.
  - **`make_interval(secs => N)` over `interval '1s' * N`:** Postgres rejects `interval '1 second' * time_limit_s` without explicit casts (`(time_limit_s)::int * interval '1 second'`), and even then it's less readable than `make_interval(secs => time_limit_s)`. `make_interval` accepts named-parameter syntax for any time unit (years, months, days, hours, mins, secs) and is the idiomatic way to compute a duration from an integer column. Apply to any future RPC computing "now + N seconds" from a stored `time_limit_s` / `cooldown_s` column.
  - **`set search_path = public` on SECURITY DEFINER:** every SECURITY DEFINER function gets `set search_path = public` in its declaration to defend against search_path-injection attacks (an attacker creating a malicious function in their schema and getting it picked up because the definer's session search_path differs from public). Apply to every future Insider/cross-game SECURITY DEFINER RPC.
  - **Calling a void RPC from supabase-js:** `supabase.rpc('fn', { p_room_id, p_round })` resolves to `{ data: null, error: null }` on success for `returns void` functions. Tests assert success via `expect(error).toBeNull()` or `expect(rpcCall()).resolves.toBeUndefined()` (when `callReconcile` ignores `data`). Reusable for `expire_round`, `advance_to_*` RPCs in upcoming Phase 5a stories.

- **Learnings:**
  - **PostgREST RPC transaction rollback is total.** When an RPC plpgsql function raises an exception, PostgREST rolls back the entire transaction wrapping the RPC call — including any side-effect UPDATE done before the raise (in this case, the `perform reconcile_round_phase(...)` first-line write). This means the natural reading of the prd phrasing "raise PGAME02 AND reconcile advances to result_failed in the same call" is impossible to satisfy literally. The realistic, design-doc-compatible behavior is: master_respond raises PGAME02, the rolled-back reconcile leaves phase='asking', and the next RPC (any client touching the round) re-runs reconcile and flips the phase — that's the T-2.A self-healing contract working as designed. The integration test explicitly calls `reconcile_round_phase` after the PGAME02 raise to verify the idempotent flip. Reusable insight for any future "raise + side-effect" RPC: if you need both, you must either (a) accept the rollback and verify the self-heal via a follow-up call, (b) use `dblink` for an autonomous transaction (heavy; available locally — `pg_extension` listing confirmed `dblink` is in `pg_available_extensions`), or (c) restructure the RPC to return a status code instead of raising. In this codebase we go with (a) and document it.
  - **Master-only role check pattern:** `left join game_insider_roles ro on (room_id, round_number, player_id)` against the caller, then `if v_role is null or v_role <> 'master'` covers both "no role row for this player" (stranger / wrong round) and "wrong role" (insider, player) in a single branch. Reusable for any role-gated RPC.
  - **Phase ordering (master-only-then-expiry-then-phase):** with reconcile run first, the migration checks role → expiry (`v_phase = 'result_failed'` ⇒ PGAME02) → phase mismatch (PGAME16). This ordering matters because once reconcile flips an expired round, the phase IS 'result_failed' — distinguishing "you ran out of time" (PGAME02) from "wrong phase entirely" (PGAME16) requires checking result_failed FIRST. Reusable for `mark_correct_guess` (US-046) which has the same expiry semantics in 'asking'.
  - **Test fixture pattern for insider RPCs:** factory `createRoomWithRoles(code, phase, {timeLimitS, startedAtIso})` inserts a room + 3 players (master/insider/player) + a pre-populated `game_insider_round` row in the requested phase + the three role rows in one helper. Lets each test specify exactly the (phase, expiry) it wants without re-running the full `start_insider_round` flow. Reusable for upcoming `mark_correct_guess` / `cast_vote` / `advance_to_reveal` tests.
